# 胎児心臓超音波の動画要約をプラグイン化する（UVS プラグイン）

> **出自**: 別リポジトリ `tatsunidas/UltrasoundVideoSummarization-Web`（private・以下 UVS-Web）の機能を
> GRAPHY-Next のプラグインとして作り直す。UVS-Web は Spring Boot ＋ React ＋ Electron の
> **フルアプリ**で、**その DICOM 層・動画層・ffmpeg 同梱は GRAPHY-Next から逆輸入したもの**
> （向こうの `fw/dicom-data-layer.md` 冒頭が「下敷き: GRAPHY-Next」と明記している）。
>
> 🔑 **だから移植するのは解析コアだけでよい。** 器は既にこちらにある。

## 0. 何をする機能か

胎児心臓超音波の**動画（数千フレーム）**から「**心臓が写っているフレーム**」を推定し、
不要なフレーム（カラードプラ・静止・心臓が写っていない）を落として**要約**する。

- 入力: **DICOM US Multi-frame（H.264 encapsulated・Modality=US）**、720×536 前後・25〜30fps・3,000〜5,000 フレーム
- 出力: 採用フレームの一覧（＋除外理由）と、それを見せる画面
- 判定: **ロジスティック回帰**（放射線特徴量 15 個）。深層学習ではない

## 1. 🔑 移植の全体像 — 持ち込むのは約 3,000 行だけ

| UVS-Web の層 | 移植するか | 理由 |
| :- | :- | :- |
| `analysis/`（FrameScorer / SummaryComposer / candidate / roi / flow） | ✅ **する**（約 1,800 行） | これが機能の本体 |
| `radiomics/`（RoiCropper / RadiomicsFeatureService） | ✅ **する**（薄い） | RadiomicsJ の呼び方だけ |
| `ml/`（推論） | ✅ **するが作り直す**（下記 §3） | ONNX をやめる |
| `common/Indices` | ✅ する | 0/1-based の集約。ここを写さないと事故る |
| `dicom/`・`video/`・`importer/`・`export/` | ❌ **しない** | **GRAPHY-Next に同じものがある**（逆輸入元） |
| `web/`（REST）・`frontend/`・`desktop/` | ❌ しない | プラグインの器に置き換える |
| `batch/`・`job/` | ❌ v1 ではしない | まず 1 本を通す |

### 1.1 ✅ ONNX を丸ごと落とす（依存が 1 つ消える）

UVS-Web は Smile の Java 直列化をやめて **ONNX（onnxruntime 1.28.0）**へ移したが、
**移植先では ONNX も要らない。**

- `models/uvs-lr-20250611/reference-params.json` に**モデルの全パラメータ**がある
  （`featureNames` / `mu` / `scale` / `coef` / `intercept`）
- 推論は `p = sigmoid(intercept + Σ coefᵢ·(xᵢ − muᵢ) / scaleᵢ)` の**算術だけ**
- 🔴 **そもそも `model.onnx` はリポジトリに存在しない**（`.gitignore` 済み。clone 直後は推論が動かない）。
  ONNX 経路は「再生成してから使う」もので、移植先に持ち込む価値が無い

⚠️ **`positiveClassIndex = 0`** で 1 列出力なので、**シグモイドの向きを取り違えると確率が反転する**。
移植時に**元アプリと同じ入力で同じ確率が出ること**を数値で確かめる（§6）。

## 2. 🔴 決めたこと（着手前の 3 つ）

### 2.1 standalone 限定にする

特徴抽出に **RadiomicsJ（Java）**が要る。プラグインの backend 面（JAR）は
**web モードでは常に 501**（サンドボックス未実装）なので、この機能は **standalone 限定**になる。

**フロントだけで完結させる道は採らない。** 15 個の IBSI 特徴（GLCM / GLDZM / NGTDM / GLRLM /
Shape2D / IntensityHistogram）を TypeScript で書き直すことになるが、
🔴 **RadiomicsJ と 1 つでも値が食い違えば、学習済みモデルの係数が意味を失う**。
「同じ特徴のつもりで別の量を入れる」ことになり、確率が静かにずれる。

⚠️ UVS-Web 自身もデスクトップ版が主戦場なので、実運用上の後退は小さい。

### 2.2 RadiomicsJ の版差は「2.4.0 で通して突き合わせる」

| | 版 |
| :- | :- |
| モデルの学習時（manifest の `featureExtraction.version`） | **2.1.16** |
| GRAPHY-Next の backend（`backend/pom.xml`） | **2.4.0** |

🔴 **IBSI 特徴の実装が版で変わっていれば、特徴量が静かにずれて確率が変わる。**
プラグイン JAR に 2.1.16 を同梱しても**解決しない**——プラグインのクラスローダは
親（アプリ）が優先なので、**本体の 2.4.0 が勝つ**。

→ **2.4.0 で動かし、元アプリの出力と 15 特徴を 1 つずつ突き合わせる**（§6 の受け入れ条件）。
ずれたら「その特徴だけ差が出る」と分かるので、**再学習か版固定かを事実に基づいて選べる**。
🚨 **突き合わせずに「たぶん同じ」で進めない。** それをやると、
**動いているように見えて確率だけが違う**という、いちばん見つけにくい壊れ方になる。

### 2.3 v1 の範囲は「解析して見せる」まで。要約シリーズの書き出しは v2

元アプリは採用フレームを **H.264 で再エンコードした派生シリーズ**として書き出す。
しかし host API の `saveDerivedSeries` は**画素配列（`frames[].data`）を受け取る口**で、
**動画シリーズは書けない**。

→ v1 は **解析 → 採用フレームの提示 → レポートへの差し込み（H39）** まで。
書き出しは「host API を足す」話になるので**別途設計する**（§8）。

## 3. 入力データをどう取るか — ここが最大の技術的争点

### 3.1 🔴 いまの GRAPHY-Next では、このデータのフレームを取れない

2 段構えで塞がっている。

| # | 何が | 状態 |
| :- | :- | :- |
| 1 | **Modality=US のマルチフレームがフレーム軸に展開されない** | `SeriesLayoutAssembler` はマルチフレーム展開を SEG / NM / XA / IVUS の 4 つにしか委譲せず、それ以外は `NumberOfFrames` を**一切見ない**（2026-09-03 に IVUS で塞いだときの「既知の穴」） |
| 2 | **展開しても Cornerstone が H.264 を解けない** | XA / IVUS の展開が効くのは**非圧縮や JPEG のフレーム**だから。対象データは **MPEG-4 AVC/H.264（TS `1.2.840.10008.1.2.4.102`）**で、`imageIdForXaFrame` 方式では読めない |

🔑 **したがって `UsFrameExpander` を足しても解決しない。**（IVUS のときと違い、ここは器を写すだけでは済まない。）

### 3.2 採る方式: **プラグインの backend 面が ffmpeg でフレームを取り出す**

GRAPHY-Next は**既に**同じことをしている:

- `fw/nondicom-ffmpeg.md` … **ffmpeg を同梱**し、CLI で「MP4(H.264 High) へ変換 → DICOM に encapsulate」
- `VideoRenderController` の `/rendered` … encapsulated PixelData から MP4 を取り出してキャッシュ
- `fw/video-viewer-design.md` … 取り込み済み Video Photographic は **encapsulated PixelData に MP4 が丸ごと**入っているので**サーバ再変換不要**

プラグインの `run()` は**同一 JVM・親クラスローダ**なので、この層をそのまま使える。

```
プラグイン backend run()
  ├ 対象 SOP の encapsulated PixelData → MP4 を取り出す（本体の仕組みを使う）
  ├ ffmpeg -f rawvideo -pix_fmt rgb24 - でフレーム列にする（ストリーミング。全フレームをメモリに載せない）
  ├ [A] 色判定 / [B] 静止判定（全フレーム）
  ├ [C] 心臓確率（間引きフレーム: ROI 抽出 → RadiomicsJ 15 特徴 → LR）
  ├ [D] 補間 → [E] 合成
  └ 結果（フレームごとのスコアと採用可否）を JSON で返す
```

⚠️ **`runBackend()` の戻りは JSON。** 4,958 フレーム × 数値 4 列で数百 KB になるので、
**返すのは配列 4 本＋要約統計だけ**にし、ROI の矩形などは要求されたフレームだけ返す。

### 3.3 ⚠️ 進捗をどう出すか（未解決）

予測は実測で **656 秒**（4,958 フレーム）かかる。UVS-Web は**非同期ジョブ＋SSE** で進捗を出していたが、
host API の `runBackend()` は**同期の 1 往復**しかない。

**v1 の割り切り**: 解析の対象を**利用者が区間で絞れる**ようにし（例: 先頭 1,000 フレーム）、
1 回の `runBackend()` を短く保つ。🔴 **「押したら 11 分無反応」を作らない。**
区間を分けて複数回呼び、フロント側で連結する（進捗はフロントが持つ）。

## 4. 画面（プラグインのフロント面）

`openWindow()`（H30）で専用ウィンドウを開く。⚠️ OS ウィンドウではなく**同一文書内に浮かぶ窓**。

| 部品 | 中身 |
| :- | :- |
| 設定 | しきい値・抽出器・間引き間隔（既定は §5 の表そのまま） |
| 実行 | 「色判定」「静止判定」「予測」を**別々に**走らせる（元アプリと同じ。色と静止は速い） |
| タイムライン | フレームごとの確率カーブ＋しきい値のハンドル。**しきい値の変更はサーバ往復せずフロントで即時再合成** |
| カラーバー | 採用 / 予測 / カラー / 静止 / 手動 の 5 本 |
| 結果 | 除外率と内訳。🔴 **「確率で除外」はカラー・静止と重複するので足し合わせない**（元アプリの実測メモ） |

🔑 **合成（`SummaryComposer`）はフロントにも持つ。** 元アプリが Java と TS の 2 実装を
**共有ベクタ `fw/testdata/summary-composer-cases.json` で突き合わせている**ので、
そのベクタごと持ち込んで vitest で固定する。

## 5. アルゴリズムの定数（**1 つ変えるとモデルが不整合になる**）

| 段 | 定数 | 値 |
| :- | :- | :- |
| 共通 | サンプル点数 / 乱数シード | **300** / **76**（フレームごとに再シード＝全フレーム同一の固定点） |
| [A] 色 | `COLOR_THRESHOLD` / `COLOR_PIX_RATIO` | **30.0** / **0.0035** |
| [B] 静止 | `MEAN_ABS_DIFF` | **0.5** ⚠️ §7 |
| [C] 候補 | 差分の間隔 | **0.2 秒** × fps |
| [C] Farnebäck | pyrScale / levels / winSize / iterations / polyN / polySigma / 平滑 σ | **3.0 / 1 / 15 / 3 / 5 / 1.1 / 5.0** |
| [C] ボックス | 個数 / 大きさ / シード | **300** / 100–200px / **76** |
| [C] クラスタ | percentile / k / maxIter | **80.0** / **1** / 100 |
| [C] 推論 | 間引き間隔 / しきい値 | `max(1, round(fps×0.5))` / **0.75** |
| 特徴 | engine / force2D / useBinCount / maskLabel | RadiomicsJ / true / true / **255** |

🔴 **グレースケールは非加重平均 `(r+g+b)/3`**（ImageJ 既定）。
加重（0.299/0.587/0.114）にすると**元アプリと一致しない**。

🔴 **乱数の消費順序は 幅 → 高さ → X → Y。** 順序を変えると同じシードでも別の ROI になる。

⚠️ `pyrScale=3.0` は `levels==1` のため**一度も参照されない**（バグではない）。

## 6. 検証 — 「動いた」で通さない

### 6.1 受け入れ条件（元アプリとの数値一致）

同じ入力に対し、**次の 5 つが一致すること**（元アプリ `fw/swing-feature-inventory.md` §9 の基準）:

1. **CPR 列**（色画素比・全フレーム）
2. **MAD 列**（平均絶対差・全フレーム）
3. **ROI 座標**（代表矩形・間引きフレーム）
4. 🔴 **15 特徴の値**（RadiomicsJ 2.4.0 と 2.1.16 の差がここに出る・§2.2）
5. **確率列**と**最終採用インデックス**

⚠️ **4 がずれたら 5 も必ずずれる。** その場合は「再学習」か「版固定」かを選ぶことになるので、
**4 を先に見る**（1〜3 が合っていれば移植は正しく、差は RadiomicsJ の版差だと切り分けられる）。

### 6.2 実機スパイク

`automator/src/spike/uvsPluginCheck.ts`。既存の作法どおり
（`DesktopDriver` → `resetDb` → `importPaths` → プラグインを手置き → メニューから起動 →
数値は **DOM ではなく `window.__graphyDebug`** から取る）。

🚨 **「押した」と「効いた」を別々に確かめる**（2026-09-03 に 3 回踏んだ）。

### 6.3 サンプルデータ

**手元に元の AVI がある**（`~/graphy_sample_images/video/`）:

| ファイル | 中身 | 諸元 |
| :- | :- | :- |
| **`HLHS.avi`**（349MB） | **低形成左心症候群の胎児心エコー** | 720×440 / 29.97fps / **11,004 フレーム** / MJPEG |
| `K1.avi`（2.2GB） | 元アプリの検証記録にある `K1-011` と同一系統 | — |

🔴 **DICOM ラップ済みのものは無いので作る。** 元アプリの取り込みと**同じ変換**にする:

```
ffmpeg -i <in>.avi -c:v libx264 -profile:v high -level:v 4.1 -bf 0 \
       -pix_fmt yuv420p -movflags +faststart -an <out>.mp4
```
→ US Multi-frame（`1.2.840.10008.5.1.4.1.1.3.1`）/ TS `1.2.840.10008.1.2.4.102` /
Modality=`US` / `YBR_PARTIAL_420` / SamplesPerPixel=3 / 未定義長 PixelData に
**空の BOT ＋ MP4 を 1 フラグメント**。

⚠️ **`-bf 0`（B フレーム無し）は必須**。dcm4che の `MP4Parser` が受け付けない。
⚠️ **Rows / Columns は偶数**（4:2:0 の制約）。720×440 はそのまま使える。

置き場所は `bench/` ではなく**手元**（`bench/` は「ファントムと検証コードのみ」で実データを含めない方針）。

## 7. 🚨 H.264 化が静止判定を壊す（移植先で必ず出る）

元アプリの実測（同一動画 4,628 フレーム）:

| 判定 | 元の AVI | **H.264 MP4** |
| :- | -: | -: |
| カラー（CPR > 0.004） | 2,437 | 2,424（−0.5%） |
| **静止（MAD < 0.5）** | 105 | 🔴 **1,060（10.4 倍）** |

H.264 の動き補償・量子化が**スペックルノイズを時間方向に平滑化**するため、MAD が系統的に下がる。
**AVI の 0.5 に相当する H.264 上の閾値は約 0.19。**

元アプリは「**圧縮前の元動画で 1 パス採点し、その結果を引き継ぐ**」ことで回避している。
🔴 **GRAPHY-Next は DICOM 化済みのデータしか扱わないので、この逃げ道が無い。**

→ **v1 の方針**: **H.264 上の閾値（≈0.19）を既定にし、画面に「この値は圧縮動画向け」と明記する。**
⚠️ **0.5 のまま出さない**——元アプリと同じ数字を使っているのに**10 倍の量が静止と判定される**、
という説明のつかない結果になる。
🔑 **しきい値は「動画の由来」に依存する量である**と設計に明記し、
**取り込み時の圧縮の有無を出自として画面に出す**。

## 8. 範囲外（v1 でやらないこと）と、その理由

| やらないこと | 理由 |
| :- | :- |
| **要約シリーズの書き出し** | `saveDerivedSeries` は画素配列の口で**動画を書けない**。host API の追加が要る（§2.3） |
| **DICOM SR / KOS** | 元アプリ自身が未実装。KOS は**プラグインから書く口が無い**（`KeyObjectWriter` は package-private） |
| バッチ処理 | まず 1 本を通す |
| 非同期ジョブ・SSE | `runBackend()` が同期 1 往復なので、区間分割で代替（§3.3） |
| web モード | backend 面が 501（§2.1） |
| モデルの追加・切り替え UI | v1 は同梱の 1 モデル固定 |
