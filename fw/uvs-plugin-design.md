# 胎児心臓超音波の動画要約をプラグイン化する（UVS プラグイン）

> **出自**: 別リポジトリ `tatsunidas/UltrasoundVideoSummarization-Web`（private・以下 UVS-Web）の機能を
> GRAPHY-Next のプラグインとして作り直す。UVS-Web は Spring Boot ＋ React ＋ Electron の
> **フルアプリ**で、**その DICOM 層・動画層・ffmpeg 同梱は GRAPHY-Next から逆輸入したもの**
> （向こうの `fw/dicom-data-layer.md` 冒頭が「下敷き: GRAPHY-Next」と明記している）。
>
> 🔑 **だから移植するのは解析コアだけでよい。** 器は既にこちらにある。

## 0. 何をする機能か

胎児心臓超音波の**動画（数千フレーム）**から「**心臓が写っているフレーム**」を推定し、
不要なフレーム（カラードプラ・静止・心臓が写っていない）を落として**要約**する。

- 入力: **DICOM US Multi-frame（H.264 encapsulated・Modality=US）**、720×536 前後・25〜30fps・3,000〜5,000 フレーム
- 出力: 採用フレームの一覧（＋除外理由）と、それを見せる画面
- 判定: **ロジスティック回帰**（放射線特徴量 15 個）。深層学習ではない

## 1. 🔑 移植の全体像 — 持ち込むのは約 3,000 行だけ

| UVS-Web の層 | 移植するか | 理由 |
| :- | :- | :- |
| `analysis/`（FrameScorer / SummaryComposer / candidate / roi / flow） | ✅ **する**（約 1,800 行） | これが機能の本体 |
| `radiomics/`（RoiCropper / RadiomicsFeatureService） | ✅ **する**（薄い） | RadiomicsJ の呼び方だけ |
| `ml/`（推論） | ✅ **するが作り直す**（下記 §3） | ONNX をやめる |
| `common/Indices` | ✅ する | 0/1-based の集約。ここを写さないと事故る |
| `dicom/`・`video/`・`importer/`・`export/` | ❌ **しない** | **GRAPHY-Next に同じものがある**（逆輸入元） |
| `web/`（REST）・`frontend/`・`desktop/` | ❌ しない | プラグインの器に置き換える |
| `batch/`・`job/` | ❌ v1 ではしない | まず 1 本を通す |

### 1.1 ✅ ONNX を丸ごと落とす（依存が 1 つ消える）

UVS-Web は Smile の Java 直列化をやめて **ONNX（onnxruntime 1.28.0）**へ移したが、
**移植先では ONNX も要らない。**

- `models/uvs-lr-20250611/reference-params.json` に**モデルの全パラメータ**がある
  （`featureNames` / `mu` / `scale` / `coef` / `intercept`）
- 推論は `p = sigmoid(intercept + Σ coefᵢ·(xᵢ − muᵢ) / scaleᵢ)` の**算術だけ**
- 🔴 **そもそも `model.onnx` はリポジトリに存在しない**（`.gitignore` 済み。clone 直後は推論が動かない）。
  ONNX 経路は「再生成してから使う」もので、移植先に持ち込む価値が無い

⚠️ **`positiveClassIndex = 0`** で 1 列出力なので、**シグモイドの向きを取り違えると確率が反転する**。
移植時に**元アプリと同じ入力で同じ確率が出ること**を数値で確かめる（§6）。

## 2. 🔴 決めたこと（着手前の 3 つ）

### 2.1 standalone 限定にする

特徴抽出に **RadiomicsJ（Java）**が要る。プラグインの backend 面（JAR）は
**web モードでは常に 501**（サンドボックス未実装）なので、この機能は **standalone 限定**になる。

**フロントだけで完結させる道は採らない。** 15 個の IBSI 特徴（GLCM / GLDZM / NGTDM / GLRLM /
Shape2D / IntensityHistogram）を TypeScript で書き直すことになるが、
🔴 **RadiomicsJ と 1 つでも値が食い違えば、学習済みモデルの係数が意味を失う**。
「同じ特徴のつもりで別の量を入れる」ことになり、確率が静かにずれる。

⚠️ UVS-Web 自身もデスクトップ版が主戦場なので、実運用上の後退は小さい。

### 2.2 RadiomicsJ の版差は「2.4.0 で通して突き合わせる」

| | 版 |
| :- | :- |
| モデルの学習時（manifest の `featureExtraction.version`） | **2.1.16** |
| GRAPHY-Next の backend（`backend/pom.xml`） | **2.4.0** |

🔴 **IBSI 特徴の実装が版で変わっていれば、特徴量が静かにずれて確率が変わる。**
プラグイン JAR に 2.1.16 を同梱しても**解決しない**——プラグインのクラスローダは
親（アプリ）が優先なので、**本体の 2.4.0 が勝つ**。

→ **2.4.0 で動かし、元アプリの出力と 15 特徴を 1 つずつ突き合わせる**（§6 の受け入れ条件）。
ずれたら「その特徴だけ差が出る」と分かるので、**再学習か版固定かを事実に基づいて選べる**。
🚨 **突き合わせずに「たぶん同じ」で進めない。** それをやると、
**動いているように見えて確率だけが違う**という、いちばん見つけにくい壊れ方になる。

### 2.3 v1 の範囲は「解析して見せる」まで。要約シリーズの書き出しは v2

元アプリは採用フレームを **H.264 で再エンコードした派生シリーズ**として書き出す。
しかし host API の `saveDerivedSeries` は**画素配列（`frames[].data`）を受け取る口**で、
**動画シリーズは書けない**。

→ v1 は **解析 → 採用フレームの提示 → レポートへの差し込み（H39）** まで。
書き出しは「host API を足す」話になるので**別途設計する**（§8）。

## 3. 入力データをどう取るか — ここが最大の技術的争点

### 3.1 🔴 いまの GRAPHY-Next では、このデータのフレームを取れない

2 段構えで塞がっている。

| # | 何が | 状態 |
| :- | :- | :- |
| 1 | **Modality=US のマルチフレームがフレーム軸に展開されない** | `SeriesLayoutAssembler` はマルチフレーム展開を SEG / NM / XA / IVUS の 4 つにしか委譲せず、それ以外は `NumberOfFrames` を**一切見ない**（2026-09-03 に IVUS で塞いだときの「既知の穴」） |
| 2 | **展開しても Cornerstone が H.264 を解けない** | XA / IVUS の展開が効くのは**非圧縮や JPEG のフレーム**だから。対象データは **MPEG-4 AVC/H.264（TS `1.2.840.10008.1.2.4.102`）**で、`imageIdForXaFrame` 方式では読めない |

🔑 **したがって `UsFrameExpander` を足しても解決しない。**（IVUS のときと違い、ここは器を写すだけでは済まない。）

### 3.1.1 ✅ 実機で裏付けた（2026-09-03・段 1 の 4/0）

`automator/src/spike/usVideoImportCheck.ts`。サンプルは `HLHS-600.dcm`（§6.3）。

| 見たもの | 実測 |
| :- | :- |
| 取り込み | ✅ **できる**（Modality=US として索引される） |
| レイアウト | 🔴 **nT = 1**（フレーム軸に展開されない） |
| 表示 | 🔴 **真っ黒**（`nonBlackFraction: 0`・`<video>` 要素 0）＝ **Cornerstone が H.264 を解けていない** |
| **`/video-metadata`** | ✅ **200**（`numberOfFrames: 600` / `fps: 29.97` / **`transcodeRequired: false`**） |
| **`/rendered`** | ✅ **200 / `video/mp4`** |

🔑 **「フロントでは開けないが、backend からは取れる」が確定した。** §3.2 の方式は
**推測ではなく実測に基づく判断**になった。特に **`transcodeRequired: false`**——
取り込んだ H.264 が**そのまま MP4 として取り出せる**ので、
プラグインは**再エンコードなしで**フレーム供給に入れる。

### 3.1.2 ⚠️ 副次的に分かった実害（プラグインとは別の話）→ ✅ **2026-09-08 に直した**

**この形式のシリーズは、利用者から見ると真っ黒に見えていた。**
`seriesRenderable.ts` は**除外リスト方式の fail-open**（末尾が `return RENDERABLE`）で、
US Multi-frame はどちらのリストにも無いため「開ける」と判定され、
**開いたうえで何も描かれなかった**。
🔴 **黙って真っ黒を出すのがいちばん悪い**——利用者には「壊れた」としか見えない。

**採った道は ①（動画経路へ回す）**。振り分けが **SOP クラスだけ**を見ていたのが原因で、
`VIDEO_SOP_CLASSES`（77.1.x）に US Multi-frame は入らない。**転送構文を判定に足した**:

- `InstanceDto` に `transferSyntaxUid` を追加（standalone は索引が既に持っていた。
  web(QIDO) は `AvailableTransferSyntaxUID` が返らないのが普通なので null 可）
- `seriesRenderable.ts` に `VIDEO_TRANSFER_SYNTAXES`（MPEG2 4.100/4.101・H.264 4.102〜4.106・
  HEVC 4.107/4.108 と Fragmentable 版）と `isVideoInstance()` を新設。
  `classifySeriesDisplay` / `SeriesViewer` の `hasVideo`・`videoInstances` / `StudyList` の
  代表判定をこれに寄せた
- 🔑 backend 側は**もともと SOP クラスで門を作っていない**（`/rendered`・`/video-metadata` は
  転送構文で判定）ので、フロントの振り分けだけで通った。MPEG2 は backend が ffmpeg で変換して
  配信し、変換できないときは VideoViewer が理由を出す（黙って落ちない）

検証: `seriesRenderable.test.ts` に 6 ケース追加（H.264/MPEG2 の US Multi-frame → `video`、
非圧縮・JPEG → `image`、web → `videoUnavailable`、転送構文が取れないときは SOP クラスだけで判定）。

### 3.2 採る方式: **プラグインの backend 面が ffmpeg でフレームを取り出す**

GRAPHY-Next は**既に**同じことをしている:

- `fw/nondicom-ffmpeg.md` … **ffmpeg を同梱**し、CLI で「MP4(H.264 High) へ変換 → DICOM に encapsulate」
- `VideoRenderController` の `/rendered` … encapsulated PixelData から MP4 を取り出してキャッシュ
- `fw/video-viewer-design.md` … 取り込み済み Video Photographic は **encapsulated PixelData に MP4 が丸ごと**入っているので**サーバ再変換不要**

プラグインの `run()` は**同一 JVM・親クラスローダ**なので、この層をそのまま使える。

```
プラグイン backend run()
  ├ 対象 SOP の encapsulated PixelData → MP4 を取り出す（本体の仕組みを使う）
  ├ ffmpeg -f rawvideo -pix_fmt rgb24 - でフレーム列にする（ストリーミング。全フレームをメモリに載せない）
  ├ [A] 色判定 / [B] 静止判定（全フレーム）
  ├ [C] 心臓確率（間引きフレーム: ROI 抽出 → RadiomicsJ 15 特徴 → LR）
  ├ [D] 補間 → [E] 合成
  └ 結果（フレームごとのスコアと採用可否）を JSON で返す
```

⚠️ **`runBackend()` の戻りは JSON。** 4,958 フレーム × 数値 4 列で数百 KB になるので、
**返すのは配列 4 本＋要約統計だけ**にし、ROI の矩形などは要求されたフレームだけ返す。

### 3.3 ⚠️ 進捗をどう出すか（未解決）

予測は実測で **656 秒**（4,958 フレーム・UVS-Web 側の計測）かかる。

📏 **こちらでの実測（2026-09-03・段 5）**: **1 予測あたり約 2.9 秒**
（ROI 抽出 1〜2 秒 ＋ RadiomicsJ 15 特徴 約 1 秒）。間引き間隔は `fps × 0.5`
（30fps なら 15 フレームごと）なので、4,958 フレームなら約 330 回 ＝ **16 分**。
🔴 **UVS-Web の 656 秒より遅い。** 差の出どころを確かめずに「速くなるはず」と書かないこと。

🔴 **段 6 では ffmpeg を 1 回しか起動しない。** 段 5 の検査は `readPair(a, b)` で
**毎回先頭から復号し直して**いる（1 フレームだけ見るには十分だが、330 回やると
復号だけで潰れる）。全走査は `FrameSource#forEachPair` の 1 パスに載せる。UVS-Web は**非同期ジョブ＋SSE** で進捗を出していたが、
host API の `runBackend()` は**同期の 1 往復**しかない。

**v1 の割り切り**: 解析の対象を**利用者が区間で絞れる**ようにし（例: 先頭 1,000 フレーム）、
1 回の `runBackend()` を短く保つ。🔴 **「押したら 11 分無反応」を作らない。**
区間を分けて複数回呼び、フロント側で連結する（進捗はフロントが持つ）。

## 5. アルゴリズムの定数（**1 つ変えるとモデルが不整合になる**）

| 段 | 定数 | 値 |
| :- | :- | :- |
| 共通 | サンプル点数 / 乱数シード | **300** / **76**（フレームごとに再シード＝全フレーム同一の固定点） |
| [A] 色 | `COLOR_THRESHOLD` / `COLOR_PIX_RATIO` | **30.0** / **0.0035** |
| [B] 静止 | `MEAN_ABS_DIFF` | **0.5** ⚠️ §7 |
| [C] 候補 | 差分の間隔 | **0.2 秒** × fps |
| [C] Farnebäck | pyrScale / levels / winSize / iterations / polyN / polySigma / 平滑 σ | **3.0 / 1 / 15 / 3 / 5 / 1.1 / 5.0** |
| [C] ボックス | 個数 / 大きさ / シード | **300** / 100–200px / **76** |
| [C] クラスタ | percentile / k / maxIter | **80.0** / **1** / 100 |
| [C] 推論 | 間引き間隔 / しきい値 | `max(1, round(fps×0.5))` / **0.75** |
| 特徴 | engine / force2D / useBinCount / maskLabel | RadiomicsJ / true / true / **255** |

🔴 **グレースケールは非加重平均 `(r+g+b)/3`**（ImageJ 既定）。
加重（0.299/0.587/0.114）にすると**元アプリと一致しない**。

🔴 **乱数の消費順序は 幅 → 高さ → X → Y。** 順序を変えると同じシードでも別の ROI になる。

⚠️ `pyrScale=3.0` は `levels==1` のため**一度も参照されない**（バグではない）。

## 6. 検証 — 「動いた」で通さない

### 6.1 受け入れ条件（元アプリとの数値一致）

同じ入力に対し、**次の 5 つが一致すること**（元アプリ `fw/swing-feature-inventory.md` §9 の基準）:

1. **CPR 列**（色画素比・全フレーム）
2. **MAD 列**（平均絶対差・全フレーム）
3. **ROI 座標**（代表矩形・間引きフレーム）
4. 🔴 **15 特徴の値**（RadiomicsJ 2.4.0 と 2.1.16 の差がここに出る・§2.2）
5. **確率列**と**最終採用インデックス**

⚠️ **4 がずれたら 5 も必ずずれる。** その場合は「再学習」か「版固定」かを選ぶことになるので、
**4 を先に見る**（1〜3 が合っていれば移植は正しく、差は RadiomicsJ の版差だと切り分けられる）。

### 6.2 実機スパイク

`automator/src/spike/uvsPluginCheck.ts`。既存の作法どおり
（`DesktopDriver` → `resetDb` → `importPaths` → プラグインを手置き → メニューから起動 →
数値は **DOM ではなく `window.__graphyDebug`** から取る）。

🚨 **「押した」と「効いた」を別々に確かめる**（2026-09-03 に 3 回踏んだ）。

### 6.3 サンプルデータ

**手元に元の AVI がある**（`~/graphy_sample_images/video/`）:

| ファイル | 中身 | 諸元 |
| :- | :- | :- |
| **`HLHS.avi`**（349MB） | **低形成左心症候群の胎児心エコー** | 720×440 / 29.97fps / **11,004 フレーム** / MJPEG |
| `K1.avi`（2.2GB） | 元アプリの検証記録にある `K1-011` と同一系統 | — |

🔴 **DICOM ラップ済みのものは無いので作る。** 元アプリの取り込みと**同じ変換**にする:

```
ffmpeg -i <in>.avi -c:v libx264 -profile:v high -level:v 4.1 -bf 0 \
       -pix_fmt yuv420p -movflags +faststart -an <out>.mp4
```
→ US Multi-frame（`1.2.840.10008.5.1.4.1.1.3.1`）/ TS `1.2.840.10008.1.2.4.102` /
Modality=`US` / `YBR_PARTIAL_420` / SamplesPerPixel=3 / 未定義長 PixelData に
**空の BOT ＋ MP4 を 1 フラグメント**。

⚠️ **`-bf 0`（B フレーム無し）は必須**。dcm4che の `MP4Parser` が受け付けない。
⚠️ **Rows / Columns は偶数**（4:2:0 の制約）。720×440 はそのまま使える。

置き場所は `bench/` ではなく**手元**（`bench/` は「ファントムと検証コードのみ」で実データを含めない方針）。

## 7. 🚨 H.264 化が静止判定を壊す（移植先で必ず出る）

元アプリの実測（同一動画 4,628 フレーム）:

| 判定 | 元の AVI | **H.264 MP4** |
| :- | -: | -: |
| カラー（CPR > 0.004） | 2,437 | 2,424（−0.5%） |
| **静止（MAD < 0.5）** | 105 | 🔴 **1,060（10.4 倍）** |

H.264 の動き補償・量子化が**スペックルノイズを時間方向に平滑化**するため、MAD が系統的に下がる。
**AVI の 0.5 に相当する H.264 上の閾値は約 0.19。**

元アプリは「**圧縮前の元動画で 1 パス採点し、その結果を引き継ぐ**」ことで回避している。
🔴 **GRAPHY-Next は DICOM 化済みのデータしか扱わないので、この逃げ道が無い。**

→ **v1 の方針**: **H.264 上の閾値（≈0.19）を既定にし、画面に「この値は圧縮動画向け」と明記する。**
⚠️ **0.5 のまま出さない**——元アプリと同じ数字を使っているのに**10 倍の量が静止と判定される**、
という説明のつかない結果になる。
🔑 **しきい値は「動画の由来」に依存する量である**と設計に明記し、
**取り込み時の圧縮の有無を出自として画面に出す**。

## 8. 範囲外（v1 でやらないこと）と、その理由

| やらないこと | 理由 |
| :- | :- |
| **要約シリーズの書き出し** | `saveDerivedSeries` は画素配列の口で**動画を書けない**。host API の追加が要る（§2.3） |
| **DICOM SR / KOS** | 元アプリ自身が未実装。KOS は**プラグインから書く口が無い**（`KeyObjectWriter` は package-private） |
| バッチ処理 | まず 1 本を通す |
| 非同期ジョブ・SSE | `runBackend()` が同期 1 往復なので、区間分割で代替（§3.3） |
| web モード | backend 面が 501（§2.1） |
| モデルの追加・切り替え UI | v1 は同梱の 1 モデル固定 |

## 8.5 ✅ 段 2 の実測（2026-09-03・実機 12/0）— JAR 面の前提が確定した

## 8.6 ✅ 段 3 の実測（2026-09-03・実機 16/0）— [A] 色判定 / [B] 静止判定

`FrameScoring.java`（判定）＋ `FrameSource.java`（`/rendered` → ffmpeg で rgb24）。

### 🔑 元アプリを動かさずに検証する形をとった

比較相手は **`bench/uvs_frame_scores.py`（独立参照実装）**。元アプリのビルドと ONNX 再生成を
要さず、しかも **Java のコードを写していない**——**仕様（§5 の定数）から別に書いた**ので、

🔴 **その土台として `java.util.Random` を規格（線形合同法）から Python で再現した。**
色系（`nextInt(total)` を 300 回）・静止系（`nextInt(w)`/`nextInt(h)` を交互に 300 回）の
**両方で 8 個ずつ完全一致**することを**先に単体で**確かめてある。
ここがずれるとサンプル点が変わり、CPR も MAD も無意味になる。

### 🚨 最初は一致しなかった——原因は**検証の組み立て**の誤り

| 症状 | 読み方 |
| :- | :- |
| **先頭 3 件は完全一致**、その後ずれる | 式もサンプル点も**正しい** |
| CPR の差が **1/300 ちょうど** | **サンプル点 1 個の判定が反転**しただけ＝画素がわずかに違う |

→ **入力が違った。** 参照値を `-frames:v 60` で作り直した MP4 から出していたのに対し、
プラグインは **DICOM に埋めた 600 フレームの MP4**（`/rendered`）を見ていた。

🔑 **教訓: 不可逆圧縮を挟む検証では、参照値は「同じ符号化ストリーム」から取る。**
**同じ元動画・同じエンコード設定でも、長さが違えばレート制御が変わって画素が変わる。**
→ DICOM の encapsulated PixelData から**フラグメントを直接取り出して**参照に使う
（空 BOT の次のアイテムが MP4 本体）。

### 移植で狂いやすかった 4 点（コードに明記した）

1. **サンプル点は 2 系統**（色と静止で**同じシードでも別の点列**）
2. **点はフレームごとに作り直さない**（元は毎フレーム再シード＝全フレーム同一の 300 点。
   再現性が高いので**仕様として維持**）
3. **グレースケールは非加重平均** `(r+g+b)/3`
4. 🔴 **MAD は四捨五入した整数のグレー値で引く**（`gray()`）。丸めない `grayFloat()` は
   **差分画像を作る側**で使うもので、ここではない

### この動画の実測（実データとして妥当か）

**CPR ≈ 0.0467** で、しきい値 **0.0035** を大きく超える＝**カラードプラが入っている**。
⚠️ **静止のしきい値は動画の由来に依存する**ので、この段では**生の CPR / MAD だけを返し、
判定は呼び出し側に委ねている**（§7）。

## 8.8 🔑 段 5 の判断点 — RadiomicsJ の版差は「実在するが値に出ない」

**結論: 2.4.0 のまま進める。再学習も版固定もしない。**

学習は **2.1.16**、本体が持つのは **2.4.0**（§8.5 で実測）。計画では
「🔴 版差が出たら止めて判断する」としていた所。

### 実装前にソースの diff で当たりを付けた

**動かす前に両版の sources jar を diff した。** 15 特徴が属する 7 クラスのうち
差分があったのは 3 つだけで、**使う特徴に本当に触れるのは 2 つ**だった:

| 特徴 | 係数 | 版差の中身 |
| :- | --: | :- |
| `IntensityBasedStatistical_Percentile90` | +1.14 | 🔴 分位点の添字が `floor(p·n)` → `ceil(p·n)−1`（IBSI の nearest rank へ修正） |
| `IntensityBasedStatistical_Interquartile` | +1.33 | 🔴 同上（`getPercentile(75) − getPercentile(25)` なので同じ修正を受ける） |

**触れない**と判断したもの:
- `GLDZM_*` … 任意引数 `morphoMask` が増えただけ。**`null` なら従来と同じ経路**
- `IntensityHistogram_MinimumHistogramGradient` … 変更は**ビンが 1 本のときの保護**のみ（`nBins=32` なので通らない）
- `Shape2D_*` / `GLCM_*` / `NGTDM_*` / `GLRLM_*` … 差分 0 行

✅ **既定 `nBins` は両版とも 32**。manifest の `featureExtraction.nBins` は `null`＝
**既定値に委ねている**ので、ここが版で変わっていたら 8 特徴が一斉にずれていた。**最初に確かめる所。**

### 実測 — 同じコードを 2 版で走らせた

🔴 **突き合わせる相手は「移植元のコード」ではなく「別の版の RadiomicsJ」。**
同じコードを同じ版で走らせても一致するのは当たり前で、版差は検出できない。
→ ハーネス `RefFeat` を **2.1.16 と 2.4.0 の両方でコンパイル・実行**した（API は互換だった）。

| フレーム | 画素数 | p(2.1.16) | p(2.4.0) | Δp |
| --: | --: | --: | --: | --: |
| 0 | 25,917 | 0.999865 | 0.999865 | 0 |
| 10 | 25,440 | 0.999962 | 0.999962 | 0 |
| 20 | 27,216 | 0.999796 | 0.999796 | 0 |
| 30 | 30,975 | 0.998598 | 0.998598 | 0 |

**15 特徴すべて相対差 0。**

### 🔑 一致した理由まで確かめた（「一致したから安全」で止めない）

**順位は本当にずれている。** フレーム 10（25,440 画素）は `0.9n`・`0.75n`・`0.25n` が
いずれも整数なので、`floor` と `ceil−1` は 1 つ違う添字を指す:

| | 2.1.16 の添字 | 2.4.0 の添字 | 値 |
| :- | --: | --: | :- |
| P90 | 22896 | 22895 | 128 / 128 |
| P75 | 19080 | 19079 | 111 / 111 |
| P25 | 6360 | 6359 | 72 / 72 |

**値が同じなのは、25,440 画素が 155 段階のグレー値にしか散らばらないから**
（最頻値は 473 画素）。**隣り合う順位はほぼ確実に同値**になる。

⚠️ **これは「式が等価」なのではなく「同値が多い」だけ。** 理屈の上では
**ROI が極端に小さい**（1 段階あたりの画素が少ない）ときに値が変わりうる。

### 残る危険を数で押さえた

グレー値が 1 段だけ動いたときの影響:

| 特徴 | scale | Δz | しきい値 0.75 近傍での Δp |
| :- | --: | --: | --: |
| `Percentile90` | 25.13 | +0.045 | 約 +0.8 ポイント |
| `Interquartile` | 16.93 | +0.079 | 約 +1.4 ポイント |

**採否が変わるのは、確率がしきい値の 1.4 ポイント以内に居るフレームだけ。**
再学習の手間に見合わないので **2.4.0 で進める**。

### ⚠️ 検証できていないこと

- **padding の経路が通っていない。** 今回の 4 フレームは **NaN / Inf が 1 つも出なかった**ので、
  `model-manifest.json` の `features[].padding` を使う経路は**一度も走っていない**。
  小さすぎる ROI や単一色の ROI で初めて通る。
- **`GLDZM` の `morphoMask` を使う新しい経路は使っていない**（`null` を渡す 6 引数版のまま）。
  🔴 **上げるときにここを「改善だから」と使い始めると、学習時と違う量になる。**

### 🚨 ここで踏んだこと

**`commons-cli` がクラスパスに無く `NoClassDefFoundError` で落ちていた**のに、
**JVM が終わらなかった**ので「ハングしている」と読み違えた。CPU 使用率とスレッドの
`futex_do_wait` を 15 分ほど追いかけたが、**例外は最初から `.err` に書かれていた**。
（`main` が例外で死んでも RadiomicsJ の非デーモンスレッドが残るため `halt(0)` に届かない。）
→ **止まったらまず出力を読む。** プロセスの状態を調べるのはその後。

⚠️ 本体の中では起きない（Spring Boot の fat jar が全部持っている・親優先で解決される）。
**単体ハーネスを組むときだけの罠**だが、RadiomicsJ は `commons-cli` / `vecmath` / `poi` を要る。

#### 🚨 6-0 が UVS を壊しかけた話（記録）

真っ黒を直した直後、**スパイクが 12/9 に落ちた**。原因は「直したこと」そのもの——
シリーズが Viewer2D から**動画再生器へ移った**ため、`registerViewerCommands` の登録が無くなり
`host.getTargets()` が**空配列**を返した。`ui.js` は `imageId` を正規表現で削って
`apiBase` と SOP UID を作っていたので、対象が無い＝解析が 1 つも走らない。

→ **H1b** で塞いだ（`fw/plugin-architecture.md` §7.2）。動画は `ViewerCommands` を実装できないので
**H1 だけの登録簿**を足し、対象に `sopInstanceUid` / `apiBase` / `kind` を持たせた。
`ui.js` はこれを使い、無い host のときだけ従来の正規表現に落ちる。

🔑 **教訓**: 表示器を差し替えると、そこにぶら下がっていた host API が黙って消える。
「開けるようにした」変更が「プラグインから見えなくした」変更でもあった。

#### 6-4 で入れたもの

- `op:"compose"` … `SummaryComposer` を呼ぶだけ（規則は移植済みなので新規ロジックなし）。
  入力は 2 通り: **`heart` を直接**（共有ベクタの形）と、**`predScores` ＋ interval ＋ threshold**

- 🔴 **これは画面の常用経路ではない。** しきい値のドラッグはフロントが合成する（往復すると手が
  止まる）。この op は**フロント実装のオラクル**——規則の正本は Java 側だという関係を保つため。

#### 6-3 で入れたもの

- `op:"predict"` … サンプルを `sampleFrom` / `sampleCount` で区切って走らせ、
  `nextFrom` / `total` / `done` を返す。**進捗はフロントが持つ**。
  🔑 **中止は実装しない**——フロントが次のチャンクを投げなければ止まる（分割方式の副産物）。
- `RadiomicsFeatureService#extractDetailed` … **どの特徴が padding で埋まったか**を返す。
  `extract` はこれに委譲するので実装は 1 本のまま（数値の挙動は変えていない）。
- ⚠️ **差分の相手が範囲外なら null のまま**（`min(i+stride, last)` に丸めない）。
  元アプリは最終フレームで空画像を相手にする。丸めると別の ROI が出る。

**検証（キャッシュ経由でも段 5 と 1 ビットも違わないこと）**: 間引きを 10 にすると格子が
参照フレーム（0/10/20/30）にちょうど重なる。4 フレームすべてで **画素数・15 特徴・確率が
`worstRel = 0`**。経路は「都度復号（`readPair`）」から「キャッシュ読み出し」へ変わったが、
出る数字は同じ。

⚠️ **padding はまだ一度も通っていない**（`anyPadded: false`）。潰したのではなく、
**通ったら分かるようにした**だけ（`paddedFeatures` に特徴名が残る）。

#### 6-2 で入れたもの — 🔴 **R1（キャッシュ ≠ 復号）は閉じた**

- `FrameSource#forEachFrame(untilInclusive, sink)`（新規）… 先頭から 1 パスで流す。
  🔴 **`-ss` で途中から始めない**——シークはキーフレーム境界に丸められ、**フレーム番号が
  静かにずれる**。段 4 / 段 5 の「移植元と完全一致」は番号が合っていることに全面的に依存している。
  `readPair` は段 4/5 の検査が使うので**残した**。
- `FrameCache`（新規）… 予測に要るフレームだけを **生 rgb24 のまま** `f<index>.rgb` に置く。
  🔴 グレー値に畳んで保存すると `grayFloat` が最大 0.5 ずれて Farnebäck の入力が変わる。
  ffmpeg の第 2 出力（PNG 等）も使わない——**sink が見た `byte[]` をそのまま書く**なら
  一致は構造上の帰結になる。
- `op:"prepare"` … 復号 1 回で ①CPR 列 ②MAD 列 ③予測用フレームのキャッシュ を同時に作る。
  **始める前に空き容量を確かめて足りなければ即エラー**（黙ってディスクを埋めない）。
  🔑 **間引きの格子は動画全体で固定**（`index % interval == 0`）——区間の先頭を起点にすると
  **同じ動画でも区切り方で別の要約が出る**。チャンク分割と噛み合わない。
- `op:"checkCache"` … キャッシュと `readPair`（段 4/5 が実際に使った経路）の **md5 を比べる**。

**実測（600 フレームの HLHS サンプル・2026-09-08）**

| 見たもの | 結果 |
| :- | :- |
| CPR 列 / MAD 列 vs `bench/uvs_frame_scores.py` | **maxDiff = 0**（1 パスに作り替えても数字は 1 ビットも動いていない） |
| キャッシュ vs 復号（md5・3 サンプル） | **完全一致** |
| 復号回数 | **1**（`ffmpegRuns`） |
| 動画まるごと 1 本 | 600 フレーム走査 **1,013 ms**・サンプル 40・キャッシュ 80 枚 **73 MB** |
| `release` | 79.8 MB を実際に解放（置きっぱなしにしない） |

📏 **4,958 フレームへの外挿**: 走査 ≒ 8.4 秒、サンプル 331 × 2 枚 ≒ **767 MB**（設計の見積もりどおり）。
走査そのものは速い——**16 分かかるのは予測（RadiomicsJ ＋ LR）のほう**で、区間分割が要るのはそこ。
